# 管理员菜单与订单导入、订单价格快照及自动锁单设计

日期：2026-07-30  
项目：协作点餐 Web 应用  
状态：已获用户设计确认

## 1. 背景与目标

现有系统已经支持菜单批量导入、多人实时点单、管理员清空订单、手动锁单与历史订单查询。本次修改将管理员操作统一为更直接的文本格式，同时补齐单项管理、订单价格快照和每日自动锁单能力。

本设计的目标是：

1. 使用 `菜品名称 -- 价格` 批量覆盖当前菜单。
2. 支持清空菜单以及添加、删除单个菜单菜品。
3. 使用 `菜品名称 -- 价格 -- 数量` 批量覆盖指定日期的已点订单。
4. 支持添加、删除单个已点菜品以及清空全部已点订单。
5. 管理员批量或单项添加的点单数量显示为“管理员导入”。
6. 导入不存在于菜单中的已点菜品时，自动将其加入当前菜单。
7. 固化每个订单日期的菜品名称和价格，避免菜单修改影响历史订单。
8. 每天北京时间 23:59 自动锁定当天订单；管理员之后手动解锁时，当天不再自动锁定。
9. 所有修改继续通过现有 D1 数据库实时同步到其他设备。

## 2. 非目标

本次不实现：

- 菜品分类、图片、规格或库存管理。
- 菜单版本回滚界面。
- 自动创建下一天菜单。
- 在锁单时复制一份完整订单到另一套归档数据库。
- 为普通用户提供历史订单修改能力。

## 3. 已确认的业务规则

### 3.1 菜单批量导入

输入格式：

```text
黄瓜火腿 -- 12
麻婆豆腐 -- 12
```

规则：

- 方括号和前导 `+` 都不是输入内容的一部分。
- 批量导入采用覆盖模式，而不是追加模式。
- 导入成功后，仅本次输入中的菜品保持启用；原菜单中未出现的菜品设为停用。
- 同名历史菜品重新启用并更新价格，不创建不必要的重复记录。
- 批量操作必须先显示解析预览，再经管理员确认。

### 3.2 菜单单项管理

管理员可以：

- 添加一个菜品。
- 修改已存在同名菜品的当前价格并启用它。
- 删除一个当前菜品。
- 清空全部菜单。

“删除”和“清空”采用软删除，即将菜品设为停用，不物理删除数据库记录。这样不会破坏已有订单和历史引用。

### 3.3 已点订单批量导入

输入格式：

```text
黄瓜火腿 -- 12 -- 3
麻婆豆腐 -- 12 -- 2
```

字段依次为菜品名称、单价、数量。

规则：

- 批量导入采用覆盖模式。
- 导入目标是管理员当前选择的订单日期；默认是今天。
- 执行时删除该日期原有的全部点单贡献及订单菜品快照，再按输入重建。
- 每一行生成一条稳定的管理员导入贡献，显示名称为“管理员导入”。
- 使用固定设备身份 `admin-import` 标识导入贡献，避免重复操作产生多个虚假设备。
- 如果菜品不在当前菜单中，自动创建或重新启用该菜品，并采用输入价格作为当前菜单价格。
- 导入后普通用户可以继续通过加号和减号点选这些菜品。
- 批量覆盖必须展示预览并进行破坏性操作确认。

### 3.4 已点订单单项管理

管理员可以：

- 添加或更新一个“管理员导入”的已点菜品及数量。
- 删除所选日期的一整个已点菜品。
- 清空所选日期的全部已点订单。

删除一整个已点菜品时，删除该日期、该菜品下所有贡献者的数量，而不仅仅删除“管理员导入”的数量。该操作不删除菜单中的菜品，且必须二次确认。

清空全部已点订单时，删除所选日期的全部贡献和订单菜品快照，但保留菜单与该日期的订单元数据，并递增订单修订号，使其他设备立即刷新为空状态。

### 3.5 锁定订单

- 普通用户不能修改已锁定订单。
- 管理员也不能在锁定状态下执行批量导入、单项添加、单项删除或清空；管理员必须先明确解锁。
- 管理员仍可以手动锁定或解锁所选日期的订单。

## 4. 文本解析与校验

将当前以 Markdown 为中心的解析器拆分为两个语义明确的入口：

- `parseMenuImportText(text)`
- `parseOrderImportText(text)`

### 4.1 通用规则

- 忽略空白行。
- 对每一列执行首尾空白清理。
- 使用连续两个半角减号 `--` 作为分隔符。
- 菜品名称不能为空。
- 同一批次内菜品名称不能重复；重复时返回源文本行号，不静默合并。
- 只要任一行校验失败，整批内容不可提交，避免部分成功。
- 错误信息包含原始行号和可操作的原因。

### 4.2 菜单行

- 必须恰好有两列。
- 价格沿用现有 `parsePriceToCents` 规则。
- 价格必须大于 0，最多保留两位小数，并存储为整数分。

### 4.3 订单行

- 必须恰好有三列。
- 价格规则与菜单一致。
- 数量必须是 1 至 999 的整数。

## 5. 数据模型

### 5.1 订单菜品快照

新增 `order_items` 表，以订单日期和菜单菜品 ID 为联合主键：

```sql
CREATE TABLE order_items (
  order_date TEXT NOT NULL,
  menu_item_id TEXT NOT NULL,
  name TEXT NOT NULL,
  price_cents INTEGER NOT NULL,
  sort_order INTEGER NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  PRIMARY KEY (order_date, menu_item_id),
  FOREIGN KEY (order_date)
    REFERENCES daily_orders(order_date) ON DELETE CASCADE,
  FOREIGN KEY (menu_item_id)
    REFERENCES menu_items(id)
);
```

迁移时根据现有 `order_contributions` 与 `menu_items` 为已有订单回填快照。

之后：

- 普通用户第一次调整某个菜品时，如果当天还没有快照，则按当前菜单名称和价格创建快照。
- 管理员导入订单时，按输入名称和价格创建快照。
- 订单汇总和历史订单读取 `order_items`，不再直接使用当前 `menu_items` 的名称和价格。
- 菜单改价、停用或重新启用不会改变过去日期的金额。

### 5.2 自动锁单执行记录

新增按日期唯一的自动锁单记录表，例如：

```sql
CREATE TABLE automatic_order_locks (
  order_date TEXT PRIMARY KEY,
  locked_at TEXT NOT NULL,
  source TEXT NOT NULL
);
```

该表只记录已经成功完成的自动锁单，表达“这一天的自动锁单机会已经执行”，而不只是当前是否处于锁定状态。锁单更新、修订号更新、日志和成功记录必须放在同一个数据库批次中；批次任一写入失败时整体失败，不留下会阻止重试的半完成记录。

因此：

- 23:59 自动锁定后写入当天记录。
- 管理员随后解锁不会删除当天记录。
- 定时 Worker 或访问时补偿再次运行时看到当天记录，便不会重新锁定。
- 并发执行通过唯一主键和事务/条件写入保持幂等。

## 6. 后端模块与接口

### 6.1 菜单仓储

在现有菜单仓储基础上增加：

- 批量覆盖菜单。
- 添加或更新并启用单个菜品。
- 软删除单个菜品。
- 清空全部菜单。

每次有效修改都递增 `menu_revision`，保证客户端轮询能够及时发现变化。

### 6.2 订单仓储

扩展订单仓储以支持：

- 在普通用户首次点选时创建订单菜品快照。
- 批量替换所选日期的全部订单内容。
- 添加或更新单个管理员导入贡献。
- 删除某道菜的全部贡献和快照。
- 清空全部贡献和快照。
- 从订单快照表计算总数和金额。

所有订单写操作必须：

1. 验证订单是否锁定。
2. 在一个 D1 批次或事务语义操作中完成相关写入。
3. 递增订单修订号。
4. 写入管理员操作日志。

### 6.3 管理员 API

保留现有登录鉴权方式，增加或调整以下能力：

- 菜单批量覆盖。
- 菜单单项添加/更新。
- 菜单单项软删除。
- 清空菜单。
- 订单批量覆盖。
- 订单单项添加/更新。
- 订单单项删除。
- 清空订单。

API 返回结构化校验错误，包括行号、字段和原因。破坏性确认主要由 UI 承担，后端仍执行完整鉴权、锁定检查和输入校验。

## 8. 每日自动锁单

### 8.1 主路径：独立定时 Worker

部署一个独立 Cloudflare Worker，并将现有 D1 数据库 `order` 绑定给它。Cron 使用 UTC 表达式：

```text
59 15 * * *
```

其对应北京时间每天 23:59。Worker 必须根据定时事件时间计算 `Asia/Shanghai` 的业务日期，而不是依赖运行机器本地时区。

执行步骤：

1. 计算上海业务日期。
2. 检查该日期是否已经存在成功的自动锁单记录；存在则直接结束。
3. 确保当天 `daily_orders` 记录存在。
4. 在同一个数据库批次中将当天订单设为锁定、递增修订号、写入操作日志并插入唯一成功记录。
5. 如果唯一记录发生并发冲突，重新读取状态并按已执行处理。

### 8.2 补偿路径：请求时检查

Pages API 的订单读取与写入入口调用同一个幂等自动锁单服务：

- 请求时根据上海时间找出“最近一个已经到达 23:59 截止点的业务日期”：23:59 至午夜之间检查当天，午夜之后检查前一天。若该日期没有自动锁单成功记录，则进行补偿锁定。
- 如果存在执行记录，即使管理员已经解锁，也不再锁定。
- 如果补偿检查刚好与 Cron 并发，唯一日期记录保证最多一个路径取得执行权。

此补偿路径不替代定时 Worker，只用于处理定时任务暂时失败或部署异常。

## 9. 同步与一致性

- 菜单修改递增 `menu_revision`。
- 订单修改和锁定状态修改递增订单修订号。
- 所有设备检测到修订号变化后拉取最新快照。
- 普通用户加减号中间显示的是该菜所有贡献者数量之和，不仅是当前设备贡献。
- 管理员导入贡献也参与同一个汇总，因此导入、删除或清空后其他设备会反映最新数量。
- 覆盖和清空操作尽量以数据库批次原子执行，避免客户端观察到半完成状态。

## 10. 安全与失败处理

- 所有管理员写接口继续要求管理员会话。
- 服务端不信任客户端预览结果，提交时重新解析和校验原始输入。
- 锁定订单的修改请求返回明确冲突错误，不隐式解锁。
- D1 写入失败时不递增成功状态，也不向客户端报告成功。
- 自动创建缺失菜单菜品时遵循同名唯一性和现有 ID 生成规则。
- 清空、覆盖和整菜删除操作写入 `activity_log`，包括日期、操作者和操作类型。

## 11. 测试策略

按测试驱动顺序实施：

1. 文本解析单元测试：正常输入、空白、列数错误、价格错误、数量错误、重复菜名和准确行号。
2. 菜单仓储/API 测试：覆盖、重新启用、单项添加、软删除、清空和修订号。
3. 订单快照迁移与仓储测试：首次点单建快照、菜单改价不影响旧订单、历史汇总稳定。
4. 管理员订单 API 测试：覆盖、自动建菜单、管理员导入身份、单项添加、整菜删除、清空和锁定拒绝。
5. 自动锁单测试：北京时间日期边界、23:59 锁定、幂等、Cron 与补偿并发、管理员解锁后不再自动锁定。
6. 管理员 UI 测试：输入预览、错误提示、破坏性确认、锁定禁用和成功刷新。
7. 跨设备行为测试：管理员修改后总数量和加减控件中的数量同步更新。

## 12. 部署方案

1. 执行 D1 迁移，创建并回填 `order_items` 与自动锁单记录表。
2. 部署 Pages 应用与 Functions API。
3. 部署独立定时 Worker。
4. 将 Worker 的 D1 binding 指向现有数据库：
   - 名称：`order`
   - ID：`e238e4a3-259a-4fc3-a345-710710850249`
5. 配置并确认每天 UTC 15:59 的 Cron。
6. 在生产地址 `https://web-7ev.pages.dev/` 验证菜单覆盖、订单覆盖、单项增删、清空、跨设备数量同步与锁定状态。

## 13. 验收标准

满足以下条件即视为完成：

- 管理员能够按两列格式覆盖菜单，且能够清空、添加和删除单个菜单菜品。
- 管理员能够按三列格式覆盖指定日期已点订单，且贡献者显示为“管理员导入”。
- 管理员能够添加、删除单个已点菜品并清空全部已点订单。
- 订单导入中的缺失菜品会自动加入菜单，并可供普通用户继续加减。
- 其他设备能及时看到菜单和总数量变化，加减号中间数量正确。
- 菜单后续改价或停用不会改变历史订单名称、单价和总金额。
- 已锁定订单不能被直接修改，必须由管理员先解锁。
- 每天北京时间 23:59 自动锁单。
- 管理员在自动锁单后手动解锁，当天不会再次自动锁定。
- 完整测试、构建与生产验证通过。
